## 1. 本次确定的方向

保留现有真实浏览器登录流程。首次使用或新的浏览器环境遇到有赞短信二次验证时，自动发起本次验证码发送，用户填写验证码后由同一浏览器会话提交。确认登录成功后，保存 SID 和该账号的浏览器状态，后续优先复用。

本次只固定设计，不修改登录器、按钮、后台任务、账号配置或生产数据，不发送验证码、不提交登录，也不发布客户端。两份 2026-11-23 的新 HAR 暂不处理，不作为短信接口的实现依据。

“首次登录自动发送”指用户已主动发起连接或登录，且有赞实际要求短信验证后的自动发送步骤；已有有效 SID 或密码登录直接成功时，无需发送短信。更改短信处理不意味着恢复“保存配置就自动登录”的旧界面行为。

## 3. xxid、SID 与 CRM 凭证的区别

| 名称 | 已知来源和位置 | 后续如何处理 |
| --- | --- | --- |
| `xxid` | 页面指纹 SDK 的 JSONP 响应 `result.xxid`；对应账号登录页 Local Storage 项 `0876303504F93E80` | 随本账号浏览器状态持久化，让页面 SDK 正常读取和更新 |
| `sid` | 登录成功后浏览器接收的有赞 Cookie | 确认登录有效后，通过私有管道交给服务端加密保存，并保留浏览器 Cookie |
| CRM CSRF 及店铺凭证 | 有效 SID 正常进入对应店铺后的页面和响应 Cookie | 登录完成后按现有各店铺流程获取，分别保存 |

用户提到的“xxsid”在本设计中不设为新字段：目前明确确认的是 **xxid 和 sid 两类不同状态**，不能合并为一个凭证。xxid 不能代替 SID，也不是当前密码登录表单中需要额外拼入的参数。

### xxid 的已确认来源

1. 有赞登录页加载 SDK：`https://b.yzcdn.cn/risk-dfp-service-v2/fm.js`。
2. SDK 发起 `GET https://risk-dfp-service-v2.youzan.com/web3_8/profile.json`，请求参数由 SDK 动态生成。
3. 已有研究 HAR 的响应是 JSONP，含 `code`、`result.tokenId`、`result.xxid`、`result.xdid`；成功码为字符串 `"000"`，本次样本 xxid 长度为 88 字符。长度是样本观测，不作为通用协议常量。
4. `https://account.youzan.com` 的 Local Storage 项 `0876303504F93E80` 对应 `result.xxid`。应按 origin 保存；其他域下的同名键不是同一项存储。

本轮只读复核了 SDK 就绪实验中的三份 HAR：`baseline-073706/requests.har` 第 51 条、`fresh-073739/requests.har` 第 52 条、`ls-0876303504F93E80-073803/requests.har` 第 51 条，均捕获该接口及响应结构。条目编号从 1 开始，包含全部网络条目。

失败基线也取得了 xxid，最终仍要求短信。因此“拿到 xxid”和“登录已获信任”应分别判断，不从是否存在该键推断登录成功，也不硬编码或跨账号复制其值。

## 4. 后续登录流程

```text
用户主动发起登录
  → 检查当前 SID
    → 有效：复用，按需准备 CRM
    → 缺少或已失效：使用该用户、该账号的原浏览器目录
      → 页面 SDK 初始化 → 原页面行为与滑块 → 密码登录
        → 直接成功：确认登录并保存
        → 160210182：保留本次页面与会话
          → 自动发送本次短信一次
          → 等待用户输入 → 在同一会话中提交验证码
            → 验证成功：确认登录并保存 → 准备各店铺 CRM
            → 验证未通过：显示实际错误，不标记登录成功
```

短信分支应接在现有密码登录结果之后，不另造一套缺少浏览器状态的 HTTP 登录流程。等待验证码时保留原浏览器 context、页面及当前验证事务；不能关闭浏览器后在另一个 profile 提交。

若页面已经自动发送短信，应识别其结果，不再重复发送。同一登录事务的重复点击、前端重渲染和状态轮询不能重复发短信。等待期间不重新提交密码或重复跑滑块；是否还需额外验证，以实际页面流程为准。

## 5. 成功后的保存与后续复用

短信提交成功后，先确认有赞业务登录结果、受保护页面及 SID，再用店铺列表只读接口验证会话；不能仅凭短信发送成功、验证码格式正确或 HTTP 200 判为登录成功。店铺访问权限问题应单独报告，不归为账号登录失败。

确认成功后保存两部分：

1. **账号登录凭证**：按现有模式，将 SID 与其实际到期信息通过私有管道回收，写入当前用户对应的加密凭证记录。
2. **同账号浏览器状态**：保留原持久化 profile 中的 Cookie、Local Storage 和 SDK 状态，包括 xxid 对应项。优先沿用既有 profile，不只导出一个 xxid 字符串，也不因刷新 SID、普通 CRM 更新或重复保存相同密码而新建目录。

保存失败不得显示完成。登录或验证失败不覆盖此前成功的凭证；浏览器 SDK 运行期间自身更新状态是正常页面行为，不等于应用确认或提交了一份成功凭证。

各 Galaxy 用户、workspace、有赞连接及账号的浏览器目录继续隔离。更换账号不得沿用另一个账号的状态；不得用其他用户的成功 SID 或 xxid 修复当前连接。

下次连接先复用有效 SID；确需重新登录时复用该账号原目录，让 SDK 自行读取历史状态。若有赞再次要求短信，重新走正常验证流程；不承诺只验证一次后永久免短信，不修改客户端到期时间冒充续期。

CRM 只在登录确认后获取；短信等待期间不并发刷新 CRM。各店铺结果独立报告，已知无权限的最后一家保持现状。

## 6. 实现时需要改动的边界

| 位置 | 计划改动 |
| --- | --- |
| 登录主脚本 | 增加短信等待和提交分支，复用原浏览器；保留原密码、滑块、会话复用与账号核对逻辑 |
| 有赞登录适配器 | 把验证码等待状态转给前端，将用户提交关联到当前登录任务 |
| 进程通信层 | 支持验证码在初始启动之后传入，继续走私有管道 |
| 有赞服务与路由 | 维护当前用户的待验证任务、串行处理与成功后的凭证保存 |
| 客户端有赞页面 | 当前任务进入等待状态后显示验证码输入和提交；保持现有连接、凭证和店铺状态展示 |

现有 `run_json_process()` 只写入一份账号密码 JSON 后立即关闭 stdin，主脚本则用 `fs.readFileSync(0)` 读取到 EOF；两端均按一次性调用设计。实现前必须设计可等待后续验证码的独立交互模式，不能直接把验证码追加到已关闭的 stdin。旧模式和其他浏览器调用保持兼容。

短信等待是非终态；现有 180 秒整段超时及任务 `running`/取消逻辑需明确适配，设置有界等待时间。取消、超时、重启或配置变更后，旧验证码提交不再继续原任务；不得把过期验证码发给新任务。错误码及是否可继续输入，以实际短信流程核验结果为准，不写死未经确认的行为。

验证码提交只允许当前有权操作该连接的用户及该任务处理。日志、任务查询和客户端响应不返回密码、验证码、SID、xxid 或完整 Cookie。验证码仅用于当前提交，不长期保存；xxid 保存在服务器受限浏览器目录，SID 沿用现有加密记录。

## 7. 短信接口暂不定稿

用户确认已在新浏览器遇到短信验证，并手动发送、提交过验证码；但本次同名 HAR 和重新导出的 HAR 均为 0 字节，用户决定暂不处理。因此不能将该次短信请求写成已解析的协议。

后续实现前，需从有效抓包或实际页面流程核实：

- 短信发送与验证码提交的真实 host、path、HTTP 方法及参数名称。
- 是否携带当前密码登录事务的 ticket、CSRF、临时 token、Cookie 或其他页面上下文，以及它们各自的来源。
- 页面是否已自动发送、发送成功的业务判断、冷却/频率限制和验证码错误或过期的结果。
- 验证码提交成功后，是否还需额外完成登录请求或跳转；SID 究竟由哪一个响应下发。
- 短信验证前后 xxid、相关 Local Storage 与 Cookie 是否发生变化，后续新 SID 登录能否复用该状态。

本设计不猜测这些接口，不从历史短信登录脚本推定本次密码二次验证的协议，也不固定任何真实验证码、设备值或一次性 token。

## 8. 后续验收

1. 有效 SID 场景不提交密码、不发送短信，原有查询与 CRM 功能正常。
2. 首次或新 profile 实际要求短信时，只触发一次发送，能显示等待输入并继续同一浏览器事务。
3. 正确验证码最终完成账号登录，取得可验证的 SID；用户输入错误、发送失败、超时和取消时不误报成功、不覆盖旧凭证。
4. 关闭并重新打开连接后，仍能读取该账号保存的浏览器状态；后续 SID 到期时用同一 profile 测试，不以短时复用旧 SID 代替验证。
5. 多用户并发和不同任务的验证码不会串用；待验证任务失效后提交被拒绝。
6. 通过完整流程验证各店铺 CRM；7 家中的 1 家无权限应独立呈现，不触发再次登录或重复短信。
7. 原主脚本及研究版的改动分别可追溯；只有在用户后续明确启动实现后，才编写、测试和部署短信分支。
